# 《终端/开发工具连通与排错手册》

## 1.1 环境变量

### 1.1.1代理类

说明：下面示例中把 `127.0.0.1:7890` 替换成你自己的代理地址和端口；`NO_PROXY` 用于让本机/内网地址直连、不走代理。

```
Windows CMD示例（临时：仅当前窗口生效）：
set HTTP_PROXY=http://127.0.0.1:7890
set HTTPS_PROXY=http://127.0.0.1:7890
set NO_PROXY=localhost,127.0.0.1

永久生效用 setx（setx是持久化写入用户环境变量，之后新开的窗口都会受影响）：
setx HTTP_PROXY "http://127.0.0.1:7890"
setx HTTPS_PROXY="http://127.0.0.1:7890"
setx NO_PROXY="localhost,127.0.0.1"

Windows PowerShell示例：
$env:HTTP_PROXY="http://127.0.0.1:7890"
$env:HTTPS_PROXY="http://127.0.0.1:7890"
$env:NO_PROXY="localhost,127.0.0.1"

Linux/macOS（写入 ~/.bashrc 或 ~/.zshrc 后 source 生效）：
export http_proxy="http://127.0.0.1:7890"
export https_proxy="http://127.0.0.1:7890"
export HTTP_PROXY="http://127.0.0.1:7890"
export HTTPS_PROXY="http://127.0.0.1:7890"
export no_proxy="localhost,127.0.0.1"
export NO_PROXY="localhost,127.0.0.1"
```

### 1.1.2证书类

适用场景：调用内网/自定义证书的HTTPS接口时，出现[证书验证失败]报错
作用：指定首选信任的证书文件，让对应工具使用该证书验证服务器。不同工具的变量名不同，不可混用：

```
配置示例（Windows CMD）：
# curl
set CURL_CA_BUNDLE=C:\certs\自定义证书.pem
# python requests
set REQUESTS_CA_BUNDLE=C:\certs\自定义证书.pem
# Git
set GIT_SSL_CAINFO=C:\certs\自定义证书.pem
# Node.js
set NODE_EXTRA_CA_CERTS=C:\certs\自定义证书.pem

其他系统同理（PowerShell 用 $env:变量名="路径"；Linux/macOS 用 export 变量名="路径"）
```

常见报错：
 curl：SSL certificate problem: self signed certificate
 Python requests: CERTIFICATE_VERIFY_FAILED

解决方法：按照上面示例，把你信任的那份 CA 证书路径设到对应工具的变量名后重试。

### 1.1.3如何验证当前终端是否连上目标地址

1.验证基础网络通不通（只验证网络通路，不走代理）

```
ping 目标域名：
示例：ping baidu.com
成功示例：
Pinging baidu.com [111.63.65.103] with 32 bytes of data:
Reply from 111.63.65.103: bytes=32 time=31ms TTL=52
Reply from 111.63.65.103: bytes=32 time=35ms TTL=52
Reply from 111.63.65.103: bytes=32 time=32ms TTL=52
Reply from 111.63.65.103: bytes=32 time=33ms TTL=52

Ping statistics for 111.63.65.103:
    Packets: Sent = 4, Received = 4, Lost = 0 (0% loss),
Approximate round trip times in milli-seconds:
    Minimum = 31ms, Maximum = 35ms, Average = 32ms

失败示例：
Ping request could not find host baidu.com. Please check the name and try again.
```

2.验证DNS解析对不对（验证DNS服务器能否将域名解析为IP，不走代理）

```
nslookup 目标域名
示例：nslookup github.com
成功案例：
Server:  UnKnown
Address:  192.168.254.226

Non-authoritative answer:
Name:    github.com
Address:  20.205.243.166

失败案例：
*** Default servers are not available
Server:  UnKnown
Address:  127.0.0.1

*** UnKnown can't find github.com: No response from server

出现类似的情况说明：本机DNS解析坏了，要查本机DNS配置；或改用代理（走代理时由代理服务器替你解析域名）。
```

3.验证代理有没有真的生效

```
curl cip.cc(查询当前上网用到)
生效：返回的IP是代理出口IP
没生效：返回的是本地运营商的IP（若本就没设代理，属正常）
```

4.验收标准

```
curl -vI "https://目标地址"
通过标准：能完成TLS握手并返回HTTP状态码（如200/401/403 均说明网络与证书链路已通）
```

# 1.2Git连通

## 1.2.1Git访问远程仓库

```
1.环境准备
git --version #确认已安装
git config --global user.name "Your Name"
git config --global user.email "you@example.com"

2.建立SSH连接
ssh-keygen -t ed25519 -C "you@example.com"
cat ~/.ssh/id_ed25519.pub
将公钥添加到GitHub:Settings->SSH and GPG keys
验证ssh是否连通：ssh -T git@github.com

3.克隆与基本操作
git clone git@github.com:user/repo.git #克隆
#日常同步
git pull #拉取最新
git add .
git commit -m "feat:..."
git push

4.标准协作流程
git checkout -b dev #在本地建立dev分支
git add .
git commit -m "feat:新增流式调用脚本"
git commit -m "fix:修复429重试逻辑"
git push -u origin dev #首次推送带-u
5.在GitHub上创建Pull Request，PR应至少包含：变更内容与目的，如何本地运行，如何验证，风险与回滚方式
```

## 1.2.2Git访问远程仓库与文档站点的常见失败现象与步骤处理

```
1.终端curl无法访问文档站点
报错日志：Could not resolve host / Failed to connect port 443: Timed out
原因：DNS解析失败被污染，直连被墙，或者代理不可用
处理方式：换DNS，给终端配代理（HTTP_PROXY/HTTPS_PROXY)
验证方式：用curl继续重新尝试访问



2.Git无法访问远程仓库
2.1 SSH公钥未添加到GitHub
    现象：Permission denied (publickey)
    原因：SSH公钥未添加到GitHub
    处理方式：重新添加公钥
    验证方式：ssh -T git@github.com
2.2 DNS解析失败或被污染
    现象：Could not resolve host: github.com
    处理方式：更换DNS，终端设置代理
    验证方式：nslookup github.com
2.3 直连被阻
    现象：Failed to connect to github.com port 443: Timed out
    处理方式：配置HTTP_PROXY/HTTPS_PROXY，检查Git代理配置
    验证方式：curl -v https://github.com
            git config --global --get http.proxy
2.4 CA证书缺失，代理根证书未信任
    现象：SSL certificate problem
    处理方式：更新CA证书，将代理根证书加入系统证信任库
    验证方式： 1.确认Git读系统证书存储：git config --global --get http.sslbackend
             2.静态确认自定义 CA 已在系统根存储：Get-ChildItem Cert:\LocalMachine\Root | Where-Object { $_.Subject -like "*你的CA名称*" } | Format-List Subject, Thumbprint, NotAfter
             3.动态验证 schannel 是否实际信任它——经代理访问 HTTPS 站点：curl -v https://github.com
                                                                  git ls-remote https://github.com/git/git.git HEAD
2.5 仓库地址错误，无权限
    现象：Repository not found
    处理方式：检查仓库URL地址是否正确，申请账号权限
    验证方式：浏览器登录GitHub确认仓库可访问
2.6 远程仓库有新提交，本地落后
    现象：non-fast-forward
    处理方式：先执行git pull --rebase,解决冲突后在git add <冲突文件> ，之后git rebase --continue 最后git push
    验证方式：git status干净后在重新git push
```

# 1.3 SSL/证书

## 常见SSL报错识别与应对

```
1.3.1本地缺少根证书
报错：SSL certificate problem: unable to get local issuer certificate
原因：本机根证书库缺失
应对：把对应根证书导入系统受信任的根证书颁发机构，重启终端或软件后重试
验证：curl -vI https://目标域名 不在报证书错误

1.3.2自签证书不受信任
报错：SSL certificate problem: self-signed certificate in certificate chain
原因：目标用了自签证书，不在受信任CA链里
处理：自行将自建证书或其CA手动加入本机信任库
验证：curl/Git 不在报该证书链错误

1.3.3证书过期
报错：SSL certificate problem: certificate has expired
原因：服务器证书过期，或者本机系统时间错误导致误判过期
处理：先确认本机时间是否正常，在核实是否为服务器端证书过期
验证：排除服务器端问题且解决本机时间问题后，能用curl正常握手

1.3.4主机名不匹配
报错：SSL: certificate verify failed / Hostname mismatch
原因：证书域名与访问的主机名不符合
处理：用证书上的正确域名访问；确认代理是否把目标域名改写到了别的地址
验证：用curl -v 正确域名能够成功握手

1.3.5系统时间错乱导致误报
现象：访问正常站点确报证书过期
原因：本机时间出问题，导致系统误判
处理：校准本机时间，在重试
验证：用curl -v握手通过

1.3.6代理环境下证书问题
现象：走了代理出现CONNECT或证书报错，直连正常
原因：代理本身拦截了证书，或者是代理出了问题
处理：替换或重启代理节点，确认代理配置正确
验证：用curl -v能正确握手

1.3.7系统证书导入参考
Windows：certmgr.msc → “受信任的根证书颁发机构” → 导入 .cer/.pem。
macOS：钥匙串访问 → 系统/登录 → 导入证书 → 设为“始终信任”。
Linux（Debian/Ubuntu）：复制到 /usr/local/share/ca-certificates/，执行 sudo update-ca-certificates。
Linux（RHEL/CentOS）：复制到 /etc/pki/ca-trust/source/anchors/，执行 sudo update-ca-trust。
```

# 1.4agent工具自检

```
目标：能够对Python、Node/npm、JDK 等 Agent 依赖开发工具进行版本校验、失败判断与排障步骤
```

## 1.4.1 验证是否已经安装好了Python、Node/npm、JDK

```
命令：
python --version 
node --version
npm --version
java -version
判断标准：能打印版本号，说明工具已装且可执行，报不是内部或外部命令 /command not found代表没有安装或未加入 PATH。
```

## 1.4.2失败判断与排查步骤

```
1.命令未找到
报错(CMD)：'python'不是内部或外部命令，也不是可运行的程序
报错(Powershell):java: 术语 'java' 不会被识别为 cmdlet、函数、脚本文件或可执行程序的名称。请检查名称的拼写或验证路径是否正确(如果包含路径)，然后重试。
原因：没有安装，或者装了没加入PATH
解决方法：where.exe python(在powershell中)或者where python(在cmd中)或者which python(在Linux/macOS)看是否安装，未安装则安装，已经安装则在系统PATH中补上安装目录
验收标准：python --version能够出现正确的版本号

2.版本过久
现象：工具能跑，但是项目要求更高版本
原因：版本过旧
处理：升级版本或者用版本管理工具
验收标准：python --version显示符合要求的版本

3.Python依赖缺失
报错：VS中飘黄，或者终端显示：ModuleNotFoundError: No module named 'xxx'
原因：没有安装相应的库，或者安装到了别的python解释器中
处理：在指定python解释器安装好相应的库(python -m pip install "所需库")
验收标准:在VS中不在飘黄

4.npm包安装失败
报错：ETIMEDOUT、ECONNRESET、fetch failed（网络类）EACCES、EPERM（权限类）
原因：npm install 报权限错误或网络超时或缓存坏了
网络类：换镜像：npm config set registry https://registry.npmmirror.com
       走代理
缓存类：(清空缓存)npm cache clean --force
权限类：检查下载到哪里，不要将它下载在Windows的受保护目录上
验收标准：npm install完成

5.Java环境报错
现象：java -version，正常但运行项目报ClassNotFoundException/版本不支持
原因：JDK版本与项目不匹配，或JAVA_HOME指向错误
处理：核对JAVA_HOME与实际JDK路径；按项目要求切换JDK版本
验收标准：java -version与项目要求一致，项目能正常启动
```
